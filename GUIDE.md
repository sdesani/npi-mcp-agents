## What you're building

An MCP server over the **NPPES NPI Registry** — the public US directory of healthcare providers. No API key, no rate limit worth worrying about, strict schemas.

Six tools. Three wrap the registry. Three implement logic that exists nowhere upstream, and those are the ones that justify running a server at all.

| Tool | Does | In the API? |
|---|---|---|
| `search_provider` | Find providers by name and state | yes |
| `lookup_by_npi` | Fetch one provider by NPI | yes |
| `get_specialties` | List taxonomy codes for an NPI | yes |
| `validate_npi_format` | Luhn checksum, no network call | **no** |
| `check_provider_status` | Composite referral-eligibility check | **no** |
| `find_providers_by_specialty` | Clinical keyword → taxonomy codes | **no** |

On top sits a three-agent application driving a local model:

```
  user request
       │
       ▼
┌──────────────────┐
│   Orchestrator   │  plans and synthesises · holds no tools
└────────┬─────────┘
         ├──────────────────┐
         ▼                  ▼
┌─────────────────┐ ┌──────────────────┐
│    Discovery    │ │   Verification   │
│  2 of 6 tools   │ │   4 of 6 tools   │
└────────┬────────┘ └────────┬─────────┘
         └────────┬──────────┘
                  ▼
          MCP server (HTTPS)
                  │
                  ▼
           NPPES registry
```

The model runs on your laptop through Ollama. The server runs wherever you put it. The only coupling between them is one environment variable.

**Cost:** everything is free except hosting, which is $9/month if you want a persistent URL and $0 if a tunnel to your own machine is enough. Both paths are covered.

**Time:** about 90 minutes end to end, most of it waiting on downloads and container builds.

## Prerequisites

Written for macOS. Linux works with the obvious substitutions; Windows needs WSL2.

### Install

```bash
# skip if `brew --version` already works
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

brew install python node git cloudflared
brew install --cask docker
brew install ollama
npm install -g @anthropic-ai/claude-code
```

Launch Docker Desktop once from Applications so the daemon starts. Installing the cask doesn't do that, and `docker --version` will succeed while `docker ps` still fails.

### Authenticate and pull a model

```bash
claude login

ollama serve &
ollama pull llama3.1        # 4.7 GB
```

Under 16 GB of RAM, use `ollama pull qwen2.5:3b` (2.3 GB) and substitute it everywhere below. Either model handles tool calling; smaller general-purpose models often silently ignore the `tools` parameter.

Pre-cache the bridge Claude Desktop needs for remote servers:

```bash
npx -y mcp-remote --help
```

### Verify

```bash
python3 --version     # 3.11 or newer
node --version        # v18+
git --version
docker ps             # daemon responds
ollama list           # your model appears
claude --version
cloudflared --version
```

### Two things that catch people

**Python version.** Anything 3.11+ works, including 3.13 and 3.14. Don't pin 3.11. The Dockerfile pins `python:3.11-slim` for the container, which is unrelated to your local interpreter — they never interact.

**Virtual environments are mandatory.** macOS refuses `pip install` against the system Python, and Homebrew Python is externally managed too. Every Python command in this guide assumes an active venv:

```bash
source .venv/bin/activate
```

Your prompt gains a `(.venv)` prefix. A new terminal tab does not inherit it. If `pip` or `mcp` reports "command not found," that prefix is missing — this accounts for most early friction.

## Part 1 — The server

**Goal:** a running MCP server exposing three tools over the NPI registry.

### Set up

```bash
mkdir npi-mcp-server && cd npi-mcp-server
git init
python3 -m venv .venv
source .venv/bin/activate
printf '.venv/\n__pycache__/\n*.pyc\n.pytest_cache/\n.env\n' > .gitignore
```

### Generate

```bash
claude
```

Paste [Prompt 1](#prompt-1--the-server). Exit Claude Code when it finishes.

### Run

```bash
pip install -e .
mcp dev src/npi_mcp/server.py
```

MCP Inspector opens at `localhost:5173`.

### Verify

In the Inspector UI:

| Tool | Arguments | Expect |
|---|---|---|
| `search_provider` | `last_name=Smith`, `state=MO` | real provider records |
| `lookup_by_npi` | `npi_number=1467588907` | one full record |
| `get_specialties` | `npi_number=1467588907` | taxonomy codes |

Then confirm the route table is clean:

```bash
python -c "
from npi_mcp.server import app
for r in app.routes: print(getattr(r, 'path', r))
"
```

You want exactly one `/mcp`, plus `/health` and `/`. Two `/mcp` entries means a duplicated mount prefix — see [Routing](#routing).

### What just happened

Claude Code produced five files from one prompt. The prompt named the file structure explicitly, because layout left to an agent's discretion is layout you can't navigate later. It also pinned the SDK to `<2` — the 2.x release renames `FastMCP` to `MCPServer`, and a fresh install without the pin produces code that won't import.

The part of Prompt 1 that most affects output is the paragraph about docstrings. See [Design notes](#tool-docstrings-are-runtime-prompts).

## Part 2 — Custom tools

**Goal:** three tools that couldn't be generated from an OpenAPI spec.

### Generate

```bash
claude
```

Paste [Prompt 2](#prompt-2--custom-tools). Restart the dev server afterward.

```bash
mcp dev src/npi_mcp/server.py
```

### Verify

Six tools now. Test the happy paths and the failure paths — the failures are where agent-written code most often diverges from what you asked for.

| Tool | Arguments | Expect |
|---|---|---|
| `validate_npi_format` | `1234567890` | `is_valid: false`, reason names the expected check digit |
| `validate_npi_format` | `1467588907` | `is_valid: true` |
| `check_provider_status` | `1467588907` | `is_eligible_for_referral`, `concerns: []` |
| `check_provider_status` | `9999999999` | structured result, **no traceback** |
| `find_providers_by_specialty` | `orthopedic`, `KS` | matching providers |
| `find_providers_by_specialty` | `banana`, `KS` | empty result listing valid keywords, **no traceback** |

The last two rows are the real test. If either raises, the `ERROR HANDLING RULE` in the prompt didn't land.

### What just happened

`validate_npi_format` runs a Luhn checksum locally. NPI numbers carry a check digit, so most malformed input can be rejected without a network round trip — and a model that knows to check first behaves noticeably better.

`check_provider_status` is the interesting one. It fuses local computation, a live lookup, and four business rules into a single call:

1. Validate format — bail immediately if invalid
2. Look up in NPPES — distinguish not-found from upstream error
3. Confirm enumeration status is `A` (Active)
4. Confirm at least one taxonomy is marked primary
5. Confirm the location address is complete

It answers a question the registry has no opinion about: *can I refer a patient here?* That's the difference between a proxy and a server worth deploying.

## Part 3 — Container and deployment

**Goal:** the same image reachable over HTTPS, two different ways.

### Generate

```bash
docker ps        # daemon must be running
claude
```

Paste [Prompt 3](#prompt-3--container-and-deployment). It ends by asking Claude Code to build the image and curl the health endpoint, so failures surface immediately.

### Test locally

```bash
docker build -t npi-mcp-server .
docker run -d -p 8000:8000 --name npi-test \
  -e MCP_ALLOWED_HOSTS=localhost npi-mcp-server
sleep 6
curl -s http://localhost:8000/health
docker rm -f npi-test
```

### Choose a host

The Dockerfile is standard; anything that runs a container will take it. That portability is the point of this section as much as the deployment.

**Free tiers move.** Hugging Face Docker Spaces were free until July 2026. Koyeb's free plan was this guide's replacement recommendation until Mistral acquired them and began retiring it. Treat the table below as a snapshot.

| Host | Cost | Card | Cold start | Notes |
|---|---|---|---|---|
| **Cloudflare Tunnel** | free | **no** | none | No account. Not a deployment — the URL dies with the process. |
| **Hugging Face Spaces** | $9/mo | yes | ~48h idle | Cleanest story: `git push`, watch the build log in a browser. |
| **Google Cloud Run** | free tier | yes | sub-second | Most generous allowance, most setup. |
| **Render** | free tier | yes | 30–50s | Free web services exist; the wake is slow. |

*Accurate September 2026. Given the last two years, verify before relying on any row.*

#### Option A — Cloudflare Tunnel (free, no account)

```bash
cloudflared tunnel --url http://localhost:8000
```

It prints `https://<random-words>.trycloudflare.com`. Start the container with that hostname allowed:

```bash
docker run -d -p 8000:8000 --name npi-mcp \
  -e MCP_ALLOWED_HOSTS=<random-words>.trycloudflare.com npi-mcp-server
```

The hostname changes on every run, which is exactly why the server reads it from the environment.

#### Option B — Hugging Face Spaces ($9/month PRO)

1. **New Space** → name `npi-mcp-server` → SDK **Docker** → **Public**
2. **Settings → Variables and secrets → New variable**:

```text
MCP_ALLOWED_HOSTS = <username>-npi-mcp-server.hf.space
```

Step 2 is not optional. Without it every request to `/mcp` returns `421`. Use a *variable*, not a secret — the hostname isn't sensitive.

3. Push:

```bash
git remote add space https://huggingface.co/spaces/<username>/npi-mcp-server
git add . && git commit -m "MCP server with validation tools"
git push space main --force
```

Credentials are your HF username and a **write-scope token** from Settings → Access Tokens — not your password.

`--force` is required. Every Space is created with its own initial commit, so your history and the Space's share no ancestor. Yours wins: it carries the `app_port` frontmatter. Treat the Space as a deploy target, not a repository you collaborate in.

### Verify the deployment

Health first:

```bash
BASE=https://<your-deployment-url>
curl -s $BASE/health
```

Health doesn't exercise MCP, so probe that separately. Use `initialize` — it's the one method that works without an existing session:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -X POST $BASE/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{
       "protocolVersion":"2024-11-05","capabilities":{},
       "clientInfo":{"name":"curl","version":"1"}}}'
```

`200` is what you want. Then Inspector, with transport set to **Streamable HTTP**:

```bash
npx @modelcontextprotocol/inspector $BASE/mcp
```

### Swapping hosts

Everything downstream reads one variable:

```bash
export MCP_SERVER_URL=https://<your-deployment-url>
```

That's the entire coupling. Deploy the same image elsewhere, change the variable, and Parts 4–6 work unchanged.

Worth exercising once rather than trusting. Bring up a tunnel alongside a hosted deployment, point the variable at each in turn, re-run the agents, and confirm the output matches. This guide lost two hosts during its writing; both recoveries were this variable.

## Part 4 — Claude Desktop

**Goal:** a real client calling your deployed server.

### Configure

```bash
open -e ~/Library/Application\ Support/Claude/claude_desktop_config.json
```

```json
{
  "mcpServers": {
    "npi-lookup": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://<your-deployment-url>/mcp"]
    }
  }
}
```

Claude Desktop launches MCP servers as local processes over stdio — it does not dial an HTTPS URL. `mcp-remote` bridges the two. A bare `"url"` key is **silently ignored**, which is why a misconfigured server simply vanishes from the tools list with no error anywhere.

Quit with **Cmd+Q** — closing the window isn't enough — and reopen. A tools icon appears in the composer.

If your build has **Settings → Connectors → Add custom connector**, that accepts the URL directly and skips the bridge. Fewer moving parts; prefer it when available.

### Try a query that forces a chain

```text
I need to refer a patient to an orthopedic surgeon in Kansas.
Find some options and tell me which ones are actually eligible
for a referral right now.
```

Claude calls `find_providers_by_specialty`, then `check_provider_status` on each candidate, then summarises. Expand the tool call blocks to watch the sequence.

Nothing instructed it to chain those two in that order. It read six descriptions and worked it out — which is what the docstring emphasis in Prompt 1 bought.

## Part 5 — The agent loop

**Goal:** write by hand what an SDK parameter usually hides.

### Generate

```bash
source .venv/bin/activate
pip install ollama httpx
claude
```

Paste [Prompt 4](#prompt-4--the-agent-loop).

### Run

```bash
export MCP_SERVER_URL=https://<your-deployment-url>
export OLLAMA_MODEL=llama3.1
python loop.py
```

```text
[MODEL]  llama3.1
[TOOL]   find_providers_by_specialty
         {"specialty_keyword": "orthopedic", "state": "KS"}
         -> {"providers": [...], "message": "Found 3..."}
[MODEL]  llama3.1
[TOOL]   check_provider_status  {"npi_number": "1467588907"}
         -> {"is_eligible_for_referral": true, "concerns": []}
[MODEL]  llama3.1

Two of the three orthopedic surgeons found in Kansas are currently
eligible for referral. The third is deactivated in the registry.
```

### Prove the coupling is thin

```bash
export MCP_SERVER_URL=https://<a-different-host>
python loop.py
```

Same behaviour, no code change.

### What just happened

Three functions and a `while`:

1. `get_mcp_tools()` — ask the server what it can do, convert its schema to the model's tool format
2. `call_mcp_tool()` — execute one tool, return errors as readable text rather than raising
3. `chat()` — the loop: send, check for tool calls, execute, feed results back, repeat

Read the alternation in that output: model, tool, model, tool, answer. Every agent framework you've encountered is this pattern with more machinery around it. Under 120 lines, two dependencies.

Two details worth keeping. The **iteration cap** returns a partial result after six rounds — unbounded loops hang or run up a bill, and models don't add caps unprompted. And **errors return as strings**, so the model can retry with different arguments or explain the failure, neither of which is possible if the process crashed.

## Part 6 — Three agents

**Goal:** same loop, partitioned by what each agent can see.

### Why split

At six tools, the single loop works fine. Splitting starts paying off around fifteen to twenty:

- **Narrower tool surface** — each agent chooses among two to four options, not six
- **Independent testing** — evaluate discovery quality without eligibility logic in the way
- **A routing layer you can reason about** — the thing that keeps forty tools navigable

Build it here to understand the shape, not because this problem demands it.

### The agents

| Agent | Owns | Tools |
|---|---|---|
| **Orchestrator** | Planning, sequencing, synthesis | none — deliberately |
| **Discovery** | Finding candidates | `search_provider`, `find_providers_by_specialty` |
| **Verification** | Eligibility verdicts | `validate_npi_format`, `lookup_by_npi`, `check_provider_status`, `get_specialties` |

The orchestrator holds no tools on purpose. Give a router tools and it will use them — then you have two components doing discovery and no clear owner of the result.

### Generate and run

```bash
claude
```

Paste [Prompt 5](#prompt-5--three-agents), then:

```bash
python -m agents.main
```

```text
[ORCHESTRATOR] plan: discovery -> verification -> synthesise

[DISCOVERY]    tool: find_providers_by_specialty
               -> 3 candidates

[VERIFICATION] check_provider_status  npi=1467588907
               -> eligible, concerns: []
[VERIFICATION] check_provider_status  npi=1508875567
               -> not eligible, concerns: ['Status is D']

[ORCHESTRATOR] synthesising from 2 agent results
```

### Compare

```bash
python loop.py           # one model, six tools
python -m agents.main    # three agents, partitioned
```

Same server, same tools, same question. The answers should match; what differs is that you can now point at which component made which decision.

The mechanism is one parameter:

```python
async def tools_for_ollama(self, allowlist: list[str] | None = None)
```

Everything else is the loop from Part 5.

All five, ready to paste. These are the actual content of the project.

### Prompt 1 — the server

```text
Build a Python MCP server using the official MCP SDK (mcp[cli]).

PURPOSE
Wrap the public NPPES NPI Registry REST API at
https://npiregistry.cms.hhs.gov/api (version 2.1, no auth required)
and expose it as MCP tools.

TOOLS TO EXPOSE
1. search_provider(first_name, last_name, state) -> list[ProviderRecord]
2. lookup_by_npi(npi_number) -> ProviderRecord
3. get_specialties(npi_number) -> list[SpecialtyRecord]

TECHNICAL CONSTRAINTS
- FastMCP from mcp.server.fastmcp as the server class
- FastAPI as the HTTP transport, mounted so /mcp is the endpoint
- Pydantic v2 for every input and output model
- httpx.AsyncClient for all upstream calls, shared at module level,
  10 second timeout, max 20 connections
- A /health endpoint returning status, version, uptime_seconds
- Python 3.11+, pyproject.toml (not requirements.txt)
- Pin the SDK as mcp[cli]>=1.0,<2 . The 2.x SDK renames FastMCP to
  MCPServer and changes the API; this project targets 1.x.
- Absolute imports only inside the package (from npi_mcp.models
  import ...). Never relative imports -- `mcp dev` loads server.py
  by file path, so the module has no parent package and relative
  imports raise ImportError.
- Configure DNS-rebinding protection so the server works behind a
  public hostname. Import TransportSecuritySettings from
  mcp.server.transport_security and pass it to the FastMCP
  constructor as the transport_security argument. Build allowed_hosts
  at startup from an environment variable MCP_ALLOWED_HOSTS, a
  comma-separated list of hostnames, always including these defaults:
  localhost, localhost:*, 127.0.0.1, 127.0.0.1:* . For each hostname H
  from the variable, add H to allowed_hosts and https://H to
  allowed_origins. Log the resolved allowed_hosts at startup.
  The hostname must be runtime configuration, not a constant: the same
  image runs behind a Hugging Face hostname and behind a Cloudflare
  tunnel whose hostname changes every run.
- A GET / route returning JSON with the server name, version and the
  MCP endpoint path, so a platform root probe gets 200 instead of 404.

STRUCTURE
src/npi_mcp/__init__.py
src/npi_mcp/server.py        -- FastMCP instance + @mcp.tool() defs
src/npi_mcp/nppes_client.py  -- NPPESClient class, all httpx calls
src/npi_mcp/models.py        -- all Pydantic models
src/npi_mcp/health.py        -- health endpoint

IMPORTANT
Every tool docstring is read by an LLM at runtime to decide when to
call that tool. Write each docstring to state what the tool does,
what the parameters mean, what it returns, and when to prefer it
over the other tools. Be explicit that state is a 2-letter code.

Do not write tests yet. Do not write a Dockerfile yet.
```

### Prompt 2 — custom tools

```text
Add three new tools to the MCP server. These implement logic that
does NOT exist in the NPPES API -- they are derived intelligence
layered on top of it.

TOOL 4: validate_npi_format(npi_number) -> NPIValidationResult
Pure function, no network call, synchronous (not async).
Validates a 10-digit NPI using the Luhn checksum variant used by
CMS: prepend the constant '80840' to the first 9 digits, run
standard Luhn, compare against the 10th digit.
Return: npi_number, is_valid, check_digit_valid, reason.
The reason field must be human-readable and state the expected
check digit when validation fails.
Docstring must tell the calling model to use this BEFORE
lookup_by_npi to avoid wasted API calls on malformed input.

TOOL 5: check_provider_status(npi_number) -> ProviderStatusReport
Async. Composite eligibility check in five ordered steps:
  1. validate_npi_format -- if invalid, return immediately
  2. live NPPES lookup -- handle not-found and HTTP error separately
  3. confirm enumeration status is 'A' (Active)
  4. confirm at least one taxonomy has primary=True
  5. confirm location address has address_1, city, and state
Return: npi_number, provider_name, primary_specialty,
is_eligible_for_referral (bool), concerns (list of strings).
Each failed check appends a specific, actionable string to concerns.

TOOL 6: find_providers_by_specialty(specialty_keyword, state,
        last_name_hint='') -> SpecialtyMatchResult
Async. Maps a plain-English clinical keyword to NPPES taxonomy
codes using a module-level dict covering at minimum: cardiology,
orthopedic, pediatrics, neurology, family medicine, psychiatry,
dermatology, oncology. Search NPPES, filter results to providers
holding a matching taxonomy code.
If the keyword maps to nothing, return an empty result whose
message lists the supported keywords -- do not raise.

ERROR HANDLING RULE
Never raise a bare exception out of a tool. Every failure path
returns a structured result the calling model can reason about
and recover from. An error the model can read is worth more than
an exception it cannot.
```

### Prompt 4 — the agent loop

```text
Create loop.py in the project root: a single-file agentic loop that
drives a local Ollama model against the deployed MCP server.

THREE FUNCTIONS, IN THIS ORDER

async get_mcp_tools() -> list[dict]
  POST to {MCP_SERVER_URL}/mcp with JSON-RPC method tools/list.
  Convert each MCP tool schema into Ollama's tool format:
  {type: function, function: {name, description, parameters}}.
  The MCP inputSchema maps to parameters.

async call_mcp_tool(name: str, arguments: dict) -> str
  POST to {MCP_SERVER_URL}/mcp with JSON-RPC method tools/call.
  Return the text content from the result. On a JSON-RPC error,
  return the error message as a string -- do not raise, the model
  needs to read it.

async chat(user_query: str) -> str
  The loop itself:
    1. tools = await get_mcp_tools()
    2. messages = [{role: user, content: user_query}]
    3. call ollama.chat(model, messages, tools)
    4. if the reply has no tool_calls, print and return its content
    5. otherwise, for each tool_call: execute via call_mcp_tool,
       append the result as a {role: tool} message
    6. go back to step 3
  Cap at 6 iterations; if exceeded, return what you have and say so.

CONFIG
MCP_SERVER_URL comes from the environment with no hardcoded default
pointing at any one host. I want to switch providers by changing
one variable, not by editing this file.

PRINTING
Before each ollama call print [MODEL]. For each tool call print
[TOOL] with the name, the arguments, and the first 120 chars of
the result.

ENTRY POINT
asyncio main() reading MCP_SERVER_URL and OLLAMA_MODEL from env.
Run this query:
"I need to refer a patient to an orthopedic surgeon in Kansas.
Find options and tell me which are eligible."

CONSTRAINTS
Only ollama and httpx. Under 120 lines. Readable top to bottom.
```

### Prompt 5 — three agents

```text
Refactor loop.py into a multi-agent package under agents/.
Keep the loop mechanics identical -- the change is who runs the
loop and which tools each runner can see.

agents/mcp_client.py
  Move get_mcp_tools and call_mcp_tool into an MCPClient class.
  Add: async tools_for_ollama(allowlist: list[str] | None = None)
  which returns the converted tools filtered to the allowlist.
  This one parameter is how each agent gets a narrow tool surface.

agents/base.py
  class Agent: name, system_prompt, tool_allowlist, model.
  async run(task: str, context: dict) -> AgentResult
  run() is the loop from loop.py, but it requests tools using its
  own allowlist and prepends its system_prompt.
  AgentResult dataclass: agent_name, output, tool_calls_made,
  iterations, hit_limit.

agents/specialists.py -- two Agent instances:
  DISCOVERY  allowlist [search_provider,
    find_providers_by_specialty]. System prompt: find candidate
    providers, return NPIs and names as a list, do not assess
    eligibility, do not write prose for the end user.
  VERIFICATION  allowlist [validate_npi_format, lookup_by_npi,
    check_provider_status, get_specialties]. System prompt: given
    candidate NPIs, determine referral eligibility for each,
    report concerns verbatim, never guess when a tool errors.

  class Orchestrator holding NO MCP tools of its own. Given a
  request it:

  Print every step to stdout labelled by agent.
```

### Environment

**`pip: command not found` or `externally-managed-environment`** — the venv isn't active:

```bash
cd npi-mcp-server && source .venv/bin/activate
```

Look for `(.venv)` on your prompt. New tabs don't inherit it.

**`mcp: command not found`** — same cause. `mcp` installs *into* the venv via `pip install -e .`, so it doesn't exist on your PATH without activation.

**`ImportError: attempted relative import with no known parent package`** — `mcp dev` loads `server.py` by file path, so the module has no parent package. Convert to absolute imports:

```bash
sed -i '' -E 's/^from \.([A-Za-z_]+) import/from npi_mcp.\1 import/; s/^from \. import/from npi_mcp import/' src/npi_mcp/*.py
grep -rn "^from \." src/npi_mcp/     # should return nothing
```

Absolute imports work under both `mcp dev` and `uvicorn` because `pip install -e .` puts the package on the path. Prompt 1 requests them for this reason.

**`ModuleNotFoundError: No module named 'mcp.server.fastmcp'`** — the 2.x SDK is installed; it renamed `FastMCP` to `MCPServer`. Pin it:

```toml
dependencies = ["mcp[cli]>=1.0,<2"]
```

```bash
pip install -e . --force-reinstall
python -c "from mcp.server.fastmcp import FastMCP; print('ok')"
```

### Routing

**The endpoint 404s** — usually a duplicated mount prefix. `streamable_http_app()` already serves at `/mcp`, so mounting it under another `/mcp` puts the real endpoint at `/mcp/mcp`:

```bash
python -c "
from npi_mcp.server import app
for r in app.routes: print(getattr(r, 'path', r))
"
```

Exactly one `/mcp`. A root `GET /` returning 200 is also worth having — platform probes hit `/`, and a 404 there fills your logs with noise that reads like failure.

**Inspector shows no tools** — check the transport dropdown is **Streamable HTTP**, not SSE. Picking SSE against a streamable endpoint fails in a way that looks identical to a broken server.

### Protocol

**`406 Not Acceptable`** — expected when you open `/mcp` in a browser. Streamable HTTP requires `Accept: text/event-stream` on GET; browsers send `text/html`. The JSON error body is the server working correctly. Probe with POST instead.

**`400 Bad Request` on a POST** — in stateful mode, every method after `initialize` needs a session. A cold `tools/list` has none, so the server opens a transport, rejects the call, and terminates it. Either send `initialize` first and reuse the `mcp-session-id` header:

```bash
BASE=https://<your-deployment-url>
H='Content-Type: application/json'
A='Accept: application/json, text/event-stream'

SID=$(curl -s -D- -o /dev/null -X POST $BASE/mcp -H "$H" -H "$A" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{
       "protocolVersion":"2024-11-05","capabilities":{},
       "clientInfo":{"name":"curl","version":"1"}}}' \
  | tr -d '\r' | awk -F': ' '/^[Mm]cp-[Ss]ession-[Ii]d/{print $2}')

curl -s -X POST $BASE/mcp -H "$H" -H "$A" -H "mcp-session-id: $SID" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}'
```

Or set `stateless_http=True` on the `FastMCP` constructor so each request stands alone. Recommended for platforms that sleep and restart containers — session state can't survive that anyway.

### Host allowlist

**`421 Misdirected Request`**, with this in the container log:

```text
WARNING  Invalid Host header: your-host.example.com
```

The MCP SDK enables DNS-rebinding protection by default and its allowlist covers localhost only. Any public hostname must be declared.

Hugging Face — Settings → Variables and secrets:

```text
MCP_ALLOWED_HOSTS = <username>-npi-mcp-server.hf.space
```

Locally or behind a tunnel:

```bash
docker run -d -p 8000:8000 --name npi-mcp \
  -e MCP_ALLOWED_HOSTS=abc123.trycloudflare.com npi-mcp-server
```

Three rules that catch people:

- **Hostname only** — no `https://`, no trailing slash, no path
- **Exact match** — the only wildcard is a port pattern like `localhost:*`; there is no bare `*`
- **Tunnel hostnames rotate** on every `cloudflared` run

Confirm what the server resolved — it logs the list at startup:

```bash
docker logs npi-mcp 2>&1 | grep -i allowed
```

### Deployment

**`! [rejected] main -> main (fetch first)`** — the Space's initial commit isn't in your history. Use `git push space main --force`. If your branch is `master`: `git push space master:main --force`.

**Auth failure on push** — use a write-scope access token as the password, not your account password.

**Space builds but returns 404** — port mismatch. `app_port: 8000` in the README frontmatter must match the Dockerfile's `EXPOSE`.

**Container won't start on a small instance** — memory. Check runtime logs rather than build logs; an OOM kill only appears in the former.

**First request is very slow** — the instance slept. Curl `/health` once to wake it, then proceed.

**The tunnel URL stopped working** — quick tunnels are ephemeral. Re-run `cloudflared` and update both `MCP_SERVER_URL` and the Claude Desktop config. A stable hostname needs a Cloudflare account and a named tunnel.

### Clients

**Claude Desktop silently skips the server** — no error, no tools icon. The config is using a bare `"url"` key, which Claude Desktop can't launch. Use the `mcp-remote` bridge from [Part 4](#part-4--claude-desktop). Check what it actually attempted:

```bash
tail -50 ~/Library/Logs/Claude/mcp*.log
```

Silence means the entry was ignored. A stack trace means the bridge ran and failed — two different problems.

**Ollama never calls a tool** — wrong model. Confirm `llama3.1` or `qwen2.5`; smaller general-purpose models silently drop the `tools` parameter.

### Agents

**A loop or agent never terminates** — paste the trace back to Claude Code:

```text
The loop hit the iteration cap without producing an answer.
Here is the trace: <paste>
Tighten the system prompt so it stops once it has enough to answer,
and make the partial-result path explicit.
```

In `agents/`, name the specific agent. Verification is the usual culprit, when a tool error leaves it unsure whether to retry.

**An agent calls a tool outside its allowlist** — the filter isn't being applied. Confirm `tools_for_ollama(allowlist=...)` is called with the agent's own list rather than returning everything.

## Design notes

Four ideas that transfer to any API you wrap.

### Tool docstrings are runtime prompts

FastMCP turns your docstring into the `description` field of the tool schema. That schema is sent to the model on every turn, before the user's question. The text you wrote inside triple quotes isn't read by a developer browsing source — it's read by a model deciding what to do.

A normal docstring answers *"what does this function do?"* for someone who already chose to call it. A tool docstring answers *"of these six options, is this the right one, and what do I put in the arguments?"* The model has no source, no types beyond the schema, nobody to ask. Same syntax, different job.

Four things go wrong when they're vague:

**Wrong tool.** If `lookup_by_npi` and `check_provider_status` both say "get information about a provider," the model has no basis to choose. Name the sibling and the boundary:

```python
"""
Look up a provider's raw registry record by NPI number.
Use this when you need the underlying facts. If you need to know
whether the provider can receive a referral, use
check_provider_status instead — it applies the eligibility rules.
"""
```

**Wrong arguments.** `{"type": "string"}` can't express that `state` means `MO` rather than `Missouri`. The model guesses, the API returns nothing, and it concludes no such provider exists. One clause fixes it.

**Unnecessary work.** `validate_npi_format` needs no network. The model won't know unless told — so the docstring says *when* to use it, not just what it does: "use this BEFORE `lookup_by_npi` to reject malformed input without spending a call."

**No call at all.** If nothing maps to how a user phrases their need, the model answers from training and hallucinates. `find_providers_by_specialty` exists to bridge "orthopedic surgeon" to taxonomy code `207X00000X`; the listed keywords are what make it findable.

Test by asking indirectly and watching which tool fires:

| Question | Should call |
|---|---|
| Is 1234567890 real? | `validate_npi_format` |
| Can I send a patient to 1467588907? | `check_provider_status` |
| Who is 1467588907? | `lookup_by_npi` |
| I need a knee surgeon in Kansas | `find_providers_by_specialty` |

A wrong pick is a docstring bug. You fix it by editing prose.

### Errors are a channel to the model

The consumer of your exceptions is a language model. It can't read a stack trace, but it can read a sentence.

Distinguish the cases — `not_found`, `invalid_input`, `upstream_unavailable`, `partial_data` — and return each as structured data. `check_provider_status` returns `concerns: ["Status is 'D' (not Active)"]` rather than raising, and the model can relay that to the user or move to the next candidate. A traceback ends the conversation.

This is why Prompt 2 carries an `ERROR HANDLING RULE` as a policy rather than describing individual error paths. The agent applies it to code it hasn't written yet.

### Composite tools beat thin wrappers

Anyone can generate `GET /provider/{npi}` from a spec. The value is in what can't be generated: local computation, multi-step workflows, business rules, domain vocabulary.

`check_provider_status` fuses a checksum, a network call, and four rules into one callable unit. It answers *"can I refer here?"* — a question your domain cares about and the registry has no opinion on. That's the difference between proxying an API and offering something worth deploying.

The test: if your server could be replaced by reading the upstream docs, you haven't added anything yet.

### Treat the host as swappable

This guide was written against a free Hugging Face Docker tier that no longer exists, then revised around Koyeb's free plan, which is also being retired. Two hosts lost while writing one document.

Both recoveries were one environment variable, because the coupling was one environment variable. `MCP_SERVER_URL` is read from the environment; `MCP_ALLOWED_HOSTS` is read from the environment; nothing hardcodes a hostname.

The corollary is that a deployed server is a public endpoint with a threat model. The SDK's DNS-rebinding protection exists because a local tool and an internet-facing one are different things — and it defaults to refusing, which is the right default. Declaring your hostname is a two-minute task; discovering the requirement at 10:55 on the morning of a talk is not.

## Adapting this to your own API

The NPI registry is incidental. The pattern isn't.

1. **Swap the client.** Replace `nppes_client.py` with a client for your API. Keep the `httpx.AsyncClient` shape — shared at module level, explicit timeout, connection limit.

2. **Rewrite the models.** Your Pydantic output models are the contract between your server and the model. Strip upstream JSON down to what's needed; less noise means better reasoning.

3. **Rerun Prompt 1** with your tool names and signatures. Keep every constraint — the SDK pin, absolute imports, the host allowlist, the docstring paragraph. They're domain-independent.

4. **Find your `check_provider_status`.** This is the part worth real thought. What decision does your domain make that the API has no opinion about? Order fulfillability? Deployment readiness? Contract compliance? That composite tool is why anyone runs your server.

5. **Everything else carries over unchanged** — Dockerfile, deployment, `loop.py`, the agent package. They only know about `MCP_SERVER_URL`.

A reasonable first session: run Prompt 1 against an API you already know, get three tools working in Inspector, then spend the rest of the time on step 4.
